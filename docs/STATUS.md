## v0.2.12 のSarashina入力と長文処理

原文を示すJSONだけを送っていたため、Sarashinaが校正対象を適切に扱わず、修正案の欄へ原文と同じ文を返す例がありました。変更のない案を除くと、画面では0件になります。2,249字の小説では、JSONの出力中に空白・改行を繰り返し、8,000トークンで打ち切られた応答も確認しました。

原文の場所と依頼内容、必須のJSON項目を短く伝える前置きを追加しました。Yomiyasuの方針・参照資料は全文渡し続けます。1回の入力は1,200字、出力は4,000トークンへ抑えます。出力上限・引用符の対応を崩す修正・600字を超える修正範囲や短い引用への極端な書き足しが生じた部分は、段落・文末でさらに分けて再生成します。再分割は2段階まで、全体で最大24リクエスト・生成600秒の予算です。ロック待ちと10秒の送信間隔も時間に含めます。安全な区切りがない場合や上限に達した場合は、途中の修正を適用せず原文を残します。

修正案がないことを、誤りがないという合格にはしません。無変更の案しか返らなかった部分は結果に明記し、指摘を出させるための再試行はしません。診断情報は終了理由・時間・件数・トークン数・ハッシュに限定し、原稿やAPIエラー本文・キーを保存しません。各生成先の設定と認証は保持します。

Windowsのソース版で、同じ小説の1,100字の誤字入り原稿から3か所をSarashina3 mini自身が修正しました。PPDD Flash v1.2は実際に3件を判定し、いずれもpreservedでした。3か所以外の本文・段落・方言・時刻・余韻は、想定した原稿とUTF-8バイト単位で一致しています。所要時間は約82秒です。2,249字の元の小説は約18秒で終了し、候補0件、原文のバイト列を保持しました。この0件は校正品質の合格ではなく、PPDDも実行していません。擬音・方言・否定・時刻・絵文字とCRLFを含む89字の別の対照文も、変更せず保持しました。いずれもYomiyasu 2.1.1のrun / verifyを実行しました。

PPDDの実行はCPU / BF16 / max_length 2048で、公式標準のCPU FP32とは異なる精度設定です。長文の意味判定は変更付近の抜粋に限ります。調査中には、誤字を別の誤字へ変えた案をPPDDが意味保持と判定する例もありました。PPDDは誤字検出器や最終稿の品質保証ではありません。全長12,000字の実推論、Mac実機での推論、一般の小説全体に対する校正精度は、この確認の範囲外です。

`claude-opus-5-5`に原因調査・回復処理と、誤修正を増やさず結果を示す方針を相談しました。これは校正モデルやコード全体の品質保証ではありません。Pythonの関連回帰検査82件、画面の回帰検査31件を通過しました。Windows常設版でも実画面から同じ1,100字の原稿を送り、3か所の修正・PPDD3件の意味保持判定・run / verify・テキスト保存まで確認しました。保存した本文は想定した3か所だけの修正と一致しました。この実行は約102秒でした。Codexの登録先・スタートメニュー・共有サービスも修正版へ更新しています。READMEと新しい案内文は常設版MCPの全文点検・本文照合にも通しています。文章品質の合格を示すものではありません。詳細はverification.jsonを参照してください。

## v0.2.10 の段落分割・赤ペン演出・初回案内

Sarashinaへの1回の原文を2,000字以内に制限し、全体12,000字までの入力をコードで分割します。段落・改行・文末を優先し、原文と改行を保持します。コード・URL等の保護範囲や文字の途中を避け、安全に切れない場合は生成前に停止します。分割の判断にAPIやモデルは使いません。分割した文章は同じモデルとYomiyasuの方針で順番に生成し、すべて成功した場合だけ原文全体の修正位置へ戻します。途中の失敗を部分的な校正結果として採用しません。段落をまたぐ文脈の理解や意味保持を保証するものではありません。

PPDDの判定中は、実際に生成された候補の位置を原文の上で赤く示し、現在照合している範囲にペンが走る演出を出します。右側も入力文の該当位置を示し、修正後の本文は結果が返ってから緑で表示します。候補の表示を判定完了と取り違えないよう、未確定であることを表示します。動きを減らすOS設定ではアニメーションを止めます。進捗には原文ハッシュ・UTF-16位置・実際の判定状態だけを渡し、本文・候補文・理由は保存しません。

APIキーが未設定の場合は、公式の発行画面へ進む手順を設定内に表示します。保存済みの利用者には再取得を求めません。PPDDのCPU版に必要な空きRAMとWindowsのコミット余裕、Macの実験設定、初回の取得容量も示します。準備コマンドには空きディスクの確認を加え、取得前に不足を案内します。新規導入の追加空き目安は30GiBで、容量を保証する値ではありません。PPDDの導入は引き続きPython・uvとターミナルで行います。

利用者の指示に従い、この版ではテストスイート・実API・モデル推論・画面の実行試験は行っていません。構文とソースの静的確認のみです。以下のv0.2.9以前の実測を、今回の分割や演出の実行証拠として扱いません。Mac実機も未検証です。

## v0.2.8 の入力制限・時間上限・エラー表示

Issue #7〜#10に対応しました。MCPの1行上限は512,000バイトです。上限を超える行は、読み取りごとのメモリ使用量を制限しながら改行またはEOFまで破棄し、入力サイズのエラーを1件返します。続く要求は処理できます。

Deciderへ明示した待ち時間は、ロック取得・初回起動・推論の待機で共用します。期限が切れた要求のために新しい推論を開始しません。別の要求が使っているワーカーは、ロック待ちの時間切れを理由に停止しません。起動済みプロセスの安全な終了処理には追加時間がかかる場合があります。

Deciderの起動・推論エラーは、コードに対応する固定文案へ統一します。例外の生文字列、利用者名、絶対パス、任意の診断文字列を結果へ表示しません。調査に必要な情報は、許可した例外種別や資源量などの数値に絞ります。原文と修正候補は失敗時も残します。

CLIの検出では、未初期化のキャッシュを「未導入」と取り違えないよう修正しました。

HTTPの413・415、ループバック限定バインド、受信期限の回帰検査はv0.2.7からあります。今回、本文256,000バイトちょうどの受理と、空・負数の長さの拒否も追加しました。

WindowsとWSL上のLinuxでPython検査を各306件実行し、いずれも305件成功・環境固有の1件スキップでした。画面ロジック19件も成功しました。Windows配布exeでは、8MiBのMCP入力の拒否と次の要求への復帰、同梱ワーカーの起動エラーの秘匿、MCP・run / verify、専用EdgeChromiumウィンドウ、凍結CLI同士の認証通信を確認しました。生成サービスとモデル推論は呼んでいません。Mac実機は引き続き未検証です。

## v0.2.7 の入力・受信・共有通信の修正

Issue #3〜#5に対応しました。不正なUnicode文字（未対サロゲート）を含む原文・文体メモ・修正案・最終稿などを、処理前に入力エラーとして拒否します。原文や候補をエラーへ表示せず、再入力を案内します。有効な絵文字、UTF-16の修正位置、CRLFを保持し、入力を黙って置換・正規化しません。

HTTPの受信はリクエストごとにヘッダーと本文を合わせて30秒までとし、少量ずつ送り続けても期限を延ばしません。同時に処理する接続を32までに制限します。入力を受け取った後の長い校正やモデル処理には、この受信期限を適用しません。

ローカルDeciderの共有RPCは、本文の送信前にHMACで接続先を認証し、応答のMACも検証します。実際の待受ポート、同じTCP接続の継続、排他的なポート確保を組み合わせます。アプリと共有サービスの両方の更新が必要です。旧サービスを認証できなければ原文・候補は送らず、旧方式へ切り替えません。共有鍵は設定保存領域の `rpc/secret-v1` に置き、Windowsでは現在のユーザーのDPAPI、POSIXでは本人所有・0600で保護し、配布物へ含めません。

HMACは通信の暗号化ではありません。同じOSユーザー権限の悪意のあるプロセス、管理者、OSの通信経路を操作できる相手への保護は対象外です。モデルの判断精度、日本語品質、意味保持の保証でもありません。[安全性と限界](../SECURITY.md) / [更新方法](PLUGINS.md#共有サービスの更新)

WindowsでPython検査274件を実行し、273件成功・POSIX専用1件スキップでした。画面ロジック19件も成功しました。WSL上のLinuxではRPC認証23件とHTTP境界11件が成功し、POSIXの鍵の所有権・権限も確認しました。Windowsの配布exeではMCP・run / verify、EdgeChromiumの専用ウィンドウ、凍結CLI同士の状態取得・モデル解放の認証往復、DPAPI鍵の再利用を確認しました。合成入力だけを使い、生成サービスとモデル推論は呼んでいません。

過去版の生成・推論の実測を、この修正で再実行した結果とは扱いません。Mac実機は引き続き未検証です。
